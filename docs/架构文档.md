## 1. 架构核心原则

### 1.1 三进程固定拓扑

Hermes Agent 采用**固定三进程**部署模型，职责边界不可逾越：

```
┌─────────────────────────────────────────────────────────────────┐
│                     Wails 进程 (UI)                              │
│  frontend/src/main.ts  ·  Wails Runtime IPC  ·  事件驱动渲染     │
│  职责: 桌面窗口、用户交互、面板渲染、流式展示、本地存储UI状态       │
└────────────────────────────┬────────────────────────────────────┘
                             │ Wails Runtime (bindings + Events)
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│              Wails-Go 进程 (Bridge + Execution)                  │
│  internal/brain/ · internal/router/ · internal/eion/            │
│  Eion-tools embedded (model/broker/dispatcher/mcp/skill/plugin)  │
│  职责: TCP连接池、Protobuf编解码、LLM调用、工具执行、Capability注册 │
└────────────────────────────┬────────────────────────────────────┘
                             │ TCP/UDS 连接池(4) · 长度前缀Protobuf
                             │ panel.proto (PanelFrame)
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│              Erlang 进程 (Orchestration Brain)                   │
│  Agent-brains/ · gen_statem ReAct循环 · Mnesia持久化              │
│  职责: 唯一编排中枢、上下文组装、计划生成、审批治理、容错恢复       │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 不可违反的边界约束

| 约束 | 理由 | 违反后果 |
|------|------|---------|
| Erlang 独占编排权 | ReAct循环、Plan、审批、容错必须在OTP监督下 | 控制权泄漏导致无法保证审批和降级 |
| Go 纯粹执行 | Eino仅作为原子SDK适配器，不保存状态、不内部循环 | Go崩溃丢失会话真相，无法恢复 |
| Wails 仅交互 | 前端不持有Agent真相，所有状态经panel_server同步 | 多会话不一致，前端刷新丢状态 |
| Protobuf双通道 | 通道A(panel.proto)会话级RPC，通道B(hermes.proto)原子请求 | 协议混淆导致序列化失败 |
| 防腐层隔离 | 业务层只操作Erlang Map/Go struct，不直接触碰生成代码 | Protobuf实现细节渗透业务逻辑 |

### 1.3 与v1.x的架构演进

v2.0 在 v1.x 基础上新增/增强了以下架构层：

| 新增层 | 模块 | 职责 |
|--------|------|------|
| 规划层 | `planner_chain` | Plan-Verify-Critique单次LLM链，复杂任务分解与校验 |
| 记忆层 | `memory_tier` | 三层记忆模型(facts/preferences/workspace)，Mnesia持久化，LLM自动抽取 |
| 配置层 | `provider_store` | 多Provider配置、模型路由、凭证管理、风险策略中心 |
| 审批层增强 | `approval_store` | 全局审批队列，与provider风险策略联动 |

## 2. 系统分层架构

### 2.1 Erlang侧：Agent-brains（编排大脑）

#### 2.1.1 监督树拓扑

```
hermes_brains_sup (rest_for_one)
 ├── timing_wheel        (worker)   通用时间轮，统一调度所有定时事件
 ├── mnesia_store        (worker)   Mnesia生命周期管理、快照/恢复
 ├── state_store         (worker)   ETS持有者、FSM快照、短期对话历史
 ├── approval_store      (worker)   审批队列存储(新增: 从capability独立)
 ├── provider_store      (worker)   Provider配置/模型路由/风险策略(新增v2.0)
 ├── bridge_manager      (worker)   Go执行层TCP连接池、超时/重试/重连
 ├── agent_sup           (simple_one_for_one) 动态FSM监督者
 │    └── agent_fsm*     (transient) 每会话一个ReAct状态机
 ├── case_store          (worker)   失败案例库(负面记忆)
 ├── memory_summarizer   (worker)   会话摘要生成(Mnesia持久化)
 └── memory_tier         (worker)   三层记忆存储+LLM自动抽取(新增v2.0)

panel_server (独立启动，不在监督树内)
 └── connection_handler* (per-connection spawn)
```

**启动顺序约束**：`timing_wheel → mnesia_store → state_store → approval_store → provider_store → bridge_manager → agent_sup → case_store → memory_summarizer → memory_tier`

- `provider_store` 在 `bridge_manager` 之前启动：bridge_manager初始化时需要provider_store解析默认LLM凭证
- `memory_tier` 在 `memory_summarizer` 之后：依赖Mnesia表已创建
- `panel_server` 在监督树外独立启动：accept循环不应被监督策略影响

#### 2.2.2 执行模型

Go侧严格遵循"问什么答什么"原则：
- **无状态**：不保存会话历史，不维护多轮上下文
- **原子请求**：每个`AgentRequest`是一个独立的原子操作
- **幂等**：`req_id`作为LRU缓存键，相同请求不重复执行
- **Panic安全**：defer/recover全局捕获，panic转为错误响应
- **并发安全**：每个TCP连接独立goroutine，共享broker用sync.Map

## 5. 关键设计决策

### 5.1 Planner：单次LLM调用而非三次调用

**决策**：planner_chain使用单次LLM调用同时输出plan+self-verify+self-critique。

**理由**：
- 三次串行LLM调用会导致TTFT延迟增加6-10秒
- 单次调用可让LLM在生成计划时自我审视，质量不劣于分离调用
- 本地verify（工具可用性检查）不需要LLM，纯Erlang集合运算即可
- 20s超时降级：超时即跳过，不影响正常ReAct流程

### 5.2 Memory Tiering：全局+会话双层合并

**决策**：`session_id = <<"global">>`作为全局记忆层，读取时合并global+session。

**理由**：
- 用户事实（如名字、技术栈）应跨会话生效
- 会话特定上下文不应污染其他会话
- 同key以session层覆盖global层，支持临时偏好
- 读取时一次性合并，无运行时开销

### 5.3 Memory Extraction：异步终态抽取

**决策**：在final answer生成后异步触发LLM抽取记忆，而非每轮都抽取。

**理由**：
- 每轮抽取增加LLM调用成本和延迟
- 终态抽取有完整上下文，质量更高
- 10s debounce防止快速连续消息重复抽取
- 抽取失败静默（catch all），不影响主流程

### 5.4 Provider Config：Erlang侧中心化管理

**决策**：Provider配置存储在Erlang Mnesia中，Go侧不缓存任何凭证。

**理由**：
- Go侧无状态设计要求不在Go侧持久化任何配置
- Erlang Mnesia disc_copies天然持久化
- bridge_manager在发送LLMInferRequest前从provider_store注入api_base/api_key
- 启动时自动seed env-default provider（从app env读取）保持向后兼容

### 5.5 API Key安全：掩码输出+Mnesia存储

**决策**：API Key明文存储在Mnesia中（bridge_manager内部使用），但list/get API自动掩码为`sk-1234****`。

**理由**：
- 桌面单机应用，威胁模型为本地用户而非远程攻击
- bridge_manager需要完整Key来构建LLMInferRequest
- 前端通过panel RPC只能看到掩码版本
- 后续可升级到OS密钥环（Windows Credential Manager/macOS Keychain）

## 6. 容错与降级

| 故障场景 | 检测 | 处理 | 用户感知 |
|---------|------|------|---------|
| FSM进程崩溃 | supervisor检测 | transient重启，从state_store快照恢复 | 短暂"思考中"，自动续跑 |
| Go执行层断连 | tcp_closed/timeout | bridge_manager重连(2s轮询)，向FSM发bridge_disconnect | Agent生成降级回复，建议检查连接 |
| LLM超时 | bridge_manager 60s超时 | 返回timeout错误给FSM，由LLM决定重试/换路径 | Agent回复"请求超时，正在重试..." |
| Provider不可用 | resolve_creds返回undefined | fallback到app env配置 | 无感知（fallback到env-default） |
| Planner超时 | 20s gen_server:call超时 | 返回{skip, timeout}，跳过计划 | 无感知（走默认ReAct） |
| 记忆抽取失败 | LLM响应解析失败/超时 | 静默catch，日志记录 | 无感知 |
| Mnesia表不存在 | init时检测 | 自动创建表+seed默认数据 | 无感知 |
| 审批超时 | approval_store TTL 5min | 自动过期，FSM收到timeout | 审批超时提示 |

### 7.5 记忆手动写入工具（P0）

在Eion-tools注册三个新工具（通过tool wrapper），Erlang侧panel_tools增加描述：
- `memory_fact`：写入facts层
- `memory_preference`：写入preferences层  
- `memory_workspace`：写入workspace层

这些工具直接调用`memory_tier:put/4`（经bridge_manager的新通道或panel RPC回环）。

**实现路径**：通过PanelExec机制，Erlang经panel连接发ToolExecRequest到Wails-Go，Go侧路由到注册的tool handler。但记忆写入是Erlang内部操作，不走Go执行层——直接在agent_fsm中暴露为内部操作，或通过capability注册为Erlang-native tool。

**推荐方案**：三个记忆工具注册为"Erlang-native capability"，在agent_fsm acting阶段检测到这些工具名时直接操作memory_tier，不走bridge_manager。这样避免了跨进程开销和Go侧依赖。
