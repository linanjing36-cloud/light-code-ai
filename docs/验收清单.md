# 能力平台化改造验收清单

## 1. 文档目标

- 用于对 `docs/执行计划.md` 中的任务逐项验收
- 所有验收项必须有任务映射、证据、回归测试结果
- 验收执行主体默认由 `AGENT-D 验收组` 负责

## 2. 验收规则

- 每条验收项必须绑定唯一编号
- 每条验收项必须绑定执行计划中的任务编号
- 每条验收项必须至少有 1 条证据
- 每条验收项必须至少有 1 条回归测试
- 验收结论分为：
  - `通过`
  - `有条件通过`
  - `不通过`

## 3. 证据类型

- `E1` 页面截图
- `E2` 接口响应
- `E3` 协议报文或日志
- `E4` 自动化测试报告
- `E5` 录屏或操作录像
- `E6` 配置/元数据快照

## 4. 回归规则

- 回归至少覆盖：
  - 原有 tool 调用
  - 会话发送与流式输出
  - `brain_status`
  - `get_history`
  - 会话删除
  - 前端切会话与终态收敛

## 6. 分模块验收说明

### 6.1 统一模型与协议

- 核查 capability 统一描述结构是否存在
- 核查 `tool` 与 `capability` 的兼容策略是否存在
- 核查 panel 协议升级后旧链路是否可用

### 6.2 编排与策略

- 核查 `Agent-brains` 是否仍保持编排权
- 核查能力选择、能力裁剪、审批等待点是否在 Erlang 层生效
- 核查不允许 Wails 或 Go 保存多轮会话真相

### 6.3 运行时与生态

- 核查 registry 是否可统一注册 skill/mcp/plugin/tool
- 核查 broker 是否支持取消、超时、统一执行
- 核查 plugin/mcp 是否被纳入同一治理模型

### 6.4 前端与观测

- 核查前端是否展示 capability list
- 核查前端是否展示来源、风险、流式、轨迹
- 核查审批与错误态是否能被用户看见

#### 关键技术决策

**为什么用 `spawn` 而非 `spawn_link`？**
`spawn_link` 会让 `mock_acceptor_loop` 链接到测试进程；当 setup 进程结束或测试用例异常时，mock 进程的 exit signal 会传播回测试进程，导致 "Related process exited with reason: killed" 错误，3 个测试用例全部被 cancelled。

**为什么用 `gen_server:start` 而非 `gen_server:start_link`？**
同上，避免 `bridge_manager` 链接到测试进程导致级联终止。

**为什么用 `catch application:load/stop`？**
- `application:load(hermes_brains)` 在已加载时返回 `{error,{already_loaded,hermes_brains}}`
- `application:stop(hermes_brains)` 在未启动时返回 `{error,{not_started,hermes_brains}}`
- 用 `catch` 包裹可忽略这些错误，保证测试夹具幂等
